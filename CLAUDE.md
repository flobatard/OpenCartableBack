# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Backend FastAPI d'une plateforme pédagogique auto-hébergée (Raspberry Pi) : un prof compose des cours par blocs et les partage à ses élèves via des liens publics. Le cahier des charges complet (architecture cible, enjeux, modèle de données, roadmap J0→J5) est dans **Descriptions.md** — le lire avant tout travail de fond ; il fait foi et doit être mis à jour quand une décision d'architecture change. Les jalons J0→J2 (+ J4 anticipé) sont livrés — J1 (contenu) : taxonomie des matières, classification des niveaux d'étude, modèle BDD des cours (blocs + bibliothèque de ressources, découplés), **API des cours** (`app/courses/` : CRUD cours, structure des blocs, édition du contenu texte/exercice/document, réglages d'affichage de la preview par cours) et **bibliothèque de ressources S3** (`app/core/storage.py` + `app/resources/` : CRUD complet + flow presigned — presign PUT → confirmation HEAD → ressource `disponible`, sans création de bloc) sont en place, ainsi que le **J4 anticipé** : la **bibliothèque de modules interactifs** (`app/modules/` : code HTML/CSS/JS en base, cf. section dédiée) ; et le **J2 (liens publics élèves)** : visibilité par cours (`PUT /courses/{id}/visibility`), liens de partage prof (`app/share_links/`) et régime public sans compte avec presign côté élève (`app/public/`). S'y ajoute, hors jalon, l'**export/import de cours** (`app/course_transfer/`, archive `.zip` — cf. section dédiée). Le **J3 (recherche)** est livré : FTS Postgres `french_unaccent` sur les cours publics et les profs opt-in, régime public sans JWT (`app/search/`, cf. section dédiée). Hors jalon également, le **client IA générique multi-provider BYO token** (`app/core/ai/` sur LangChain 1.x + routes de smoke-test `app/ai/`, cf. section dédiée) prépare le J5 (IA), qui reste à livrer. L'utilisateur échange en français.

## Architecture

### Auth : resource server pur (décision structurante)
Le flow OIDC (Authorization Code + PKCE) est **entièrement géré par la SPA Angular**. L'API n'émet jamais de token et ne stocke aucune identité/mot de passe : elle valide le JWT Zitadel de chaque requête (signature RS256 via JWKS découvert depuis l'issuer, vérif issuer/audience/exp). Toute la logique IdP est **confinée dans `app/core/auth.py`** (exigence du cahier des charges : pouvoir changer d'IdP en ne touchant que ce module). Seuls réglages : `OIDC_ISSUER` et `OIDC_AUDIENCE`.

Sémantique des erreurs à préserver : pas de credentials ou token invalide → **401** + `WWW-Authenticate: Bearer` (jamais 403) ; IdP injoignable ou discovery/JWKS malformé → **503** ; jamais de 500, jamais le token dans les logs. Routes protégées = `Depends(get_current_user)` (`GET /api/v1/me` est l'exemple de référence) ; `/api/v1/health` reste public. Le second régime d'accès (J2, élèves sans compte) est en place : les routes `/api/v1/public/*` (`app/public/`) ne portent **aucune** dépendance JWT — l'autorisation (visibilité du cours + token de partage opaque, **404 uniforme sans oracle**) vit dans `app/public/service.py`, distincte de `get_current_user` ; ne jamais y exposer une donnée réservée au prof (règle d'or de `app/public/schemas.py`).

### Comptes applicatifs & onboarding (`users`)
La feature `app/users/` persiste les comptes (profs **et/ou** élèves — rôles cumulables `est_prof`/`est_eleve`) : `GET /api/v1/users/me` **auto-provisionne** la ligne au premier appel (upsert `ON CONFLICT DO NOTHING` sur `sub`, seule donnée IdP persistée avec l'e-mail en snapshot) ; `PUT /api/v1/users/me/profile` valide et enregistre le profil (système scolaire ∈ `education_levels.systeme`, niveaux du même système, matières existantes) en **remplacement complet** — il sert aussi d'édition de profil. Les M2M `user_subjects`/`user_education_levels` sont qualifiées par `contexte` (« enseigne »/« apprend ») ; profil complet ⟺ `onboarded_at` non NULL. **Invariant préservé : `get_current_user` ne touche jamais la base** — la résolution `sub → users` vit dans `app/users/service.py` (`get_or_create_by_sub`), pas dans `app/core/auth.py`. L'ordre des `execute` des fonctions du service est un contrat des tests (fausse session FIFO, `tests/test_users_api.py`).

### Configuration en couches
Priorité décroissante : variables d'env > `.env` > `config/<APP_ENV>.yaml` (`APP_ENV` par défaut : `development`). `config/*.yaml` = valeurs publiques versionnées ; `.env` = secrets et overrides locaux uniquement. `DATABASE_URL` est **assemblée** dans `app/core/config.py` depuis les composants `POSTGRES_*` (mot de passe percent-encodé) ; une URL complète collée dans `DATABASE_URL` prend le pas et est normalisée pour asyncpg (`sslmode`/`channel_binding` traduits en `ssl=`). Réglages S3 sur le même principe : `S3_ENDPOINT_URL`/`S3_REGION`/`S3_BUCKET` + TTL/plafond sont publics (YAML), `S3_ACCESS_KEY`/`S3_SECRET_KEY` sont des secrets (`.env`) ; tous ont un défaut → le conftest n'a rien à poser. Attention : `settings = get_settings()` s'évalue **à l'import** — dans les tests, les variables d'env sont posées en tête de `tests/conftest.py` avant tout import de `app.*` ; conserver cet ordre.

### Découpage
- Stack 100 % async : SQLAlchemy 2.0 + asyncpg partout, y compris `alembic/env.py`. Ne pas introduire de driver/engine synchrone.
- Package-by-feature : chaque domaine (courses, subjects, resources…) = un package `app/<feature>/` avec `schemas.py`, `service.py` (logique métier), `router.py` (HTTP), monté dans `create_app()` sous `settings.API_V1_PREFIX`.
- Les modèles SQLAlchemy vivent dans **`app/models/<nom>.py`** (un module par modèle) et doivent être importés + listés dans `__all__` de `app/models/__init__.py`, sinon Alembic autogenerate ne les voit pas.

### Taxonomie des matières (`subjects`)
Table unique **auto-référencée** (`app/models/subject.py`) : discipline (profondeur 0) → domaine (1) → sous-domaine (2) → sujet (3), profondeur flexible (une branche peut s'arrêter avant 3, CHECK en base) ; unicité `(parent_id, nom)` en `NULLS NOT DISTINCT` (Postgres 15+), FK `parent_id` en `ondelete=CASCADE`. Chaque nœud porte un `code` = chemin slug complet unique (ex. `mathematiques.algebre.algebre-lineaire`) dont dérive son id **uuid5 déterministe**. La taxonomie pré-remplie (~475 nœuds, lycée → master) vit dans **`app/subjects/seed_data.py` — module de données pur et APPEND-ONLY** : ne jamais changer `SEED_NAMESPACE` ni renommer/supprimer un `code` existant (la migration de seed idempotente `ON CONFLICT DO NOTHING` et les IDs en dépendent) ; tout ajout passe par une nouvelle data migration réutilisant `iter_rows()`. Lecture : `GET /api/v1/subjects/tree` — une seule requête SQL, arbre assemblé en O(n) dans `app/subjects/service.py` (les relations ORM `parent`/`children` ne sont pas chargées : lazy-load async interdit). Le CRUD prof arrivera au J1.

### Classification des niveaux d'étude (`education_levels`)
Même motif que `subjects`, en plus contraint : table auto-référencée (`app/models/education_level.py`) à deux profondeurs — cycle (0, ex. « Collège ») > classe (1, ex. « 6e ») —, un arbre par système scolaire (`systeme`, plusieurs pays occidentaux pour l'instant), unicité `(systeme, parent_id, nom)` en NULLS NOT DISTINCT. Chaque nœud porte les **pivots internationaux** `cite` (CITE/ISCED 2011, NULL si le nœud couvre plusieurs niveaux, ex. « Supérieur ») et `age_min`/`age_max` : c'est par eux que des cours se rapprocheront entre pays — les `nom` sont des noms propres nationaux, jamais traduits. Différence clé avec subjects : les `code` sont **écrits à la main** et préfixés système (ex. `fr.college.6e`), jamais dérivés du nom affiché. Le seed (22 nœuds, primaire → doctorat, voie générale) vit dans **`app/education_levels/seed_data.py`** — module de données pur et APPEND-ONLY, `SEED_NAMESPACE` propre et figé (distinct de celui des subjects) ; tout ajout (maternelle, voie pro, BTS/CPGE, arbre étranger) passe par une nouvelle data migration réutilisant `iter_rows()`. Lecture : `GET /api/v1/education-levels/tree` (même motif flat select + arbre O(n)). Pas de relations ORM ni de CRUD prévu ; le lien cours ↔ niveaux est implémenté (M2M `course_education_levels`, voir ci-dessous) ; le profil utilisateur (niveaux/matières par contexte) est implémenté via `app/users/`.

### Modèle des cours (`courses`, `blocks`, `resources`, `modules`)
Modèles dans `app/models/{course,block,resource,module}.py`, API dans `app/courses/` (section suivante). Un cours appartient à un user (`owner_id`, CASCADE) et est classé par deux M2M **sans qualificatif** `course_subjects`/`course_education_levels` (PK composite `course_id` en tête, index inverse pour les facettes de recherche — motif `user_subjects` sans `contexte`). Le cours porte en outre une colonne **`preview_settings` JSONB** (`default=dict`, `server_default '{}'::jsonb`) : réglages d'affichage de la preview propres au cours (typographie/mise en page), **contrat applicatif commenté dans `course.py` = l'interface `CourseStyleSettings` du front, clés camelCase** (`fontSizePx`/`headingScale`/`lineHeight`/`widthCh`/`paragraphGapEm`/`font ∈ {sans,serif}`), `{}` tant que non personnalisé (le front applique alors ses défauts), édité par remplacement complet via `PUT .../preview` (voir API des cours). Son contenu = **blocs ordonnés** : `position` SmallInteger **sans unicité `(course_id, position)`** (voulu : le réordonnancement réécrit les positions côté service ; tri stable `ORDER BY position, id`), `titre`/`description` **facultatifs et communs à tous les types** (métadonnées d'en-tête du bloc, distinctes du `content`), quatre types (CHECK `ck_blocks_type`) dont le `content` JSONB est un **contrat applicatif documenté dans la docstring de `block.py`** — `texte` (`{"markdown": ...}`, jamais de HTML brut ; formules LaTeX `$…$`/`$$…$$` admises dans la chaîne, rendues par KaTeX côté front ; les liens externes vivent dans le markdown, l'ancien type `lien` a été supprimé), `exercice` (`{"enonce": md, "questions": [{id, enonce md, type "texte_libre", reponse_attendue texte}]}` — `reponse_attendue` = corrigé du prof en texte simple, **jamais servi aux élèves** (le régime public J2 le filtre **structurellement** — reconstruction du content dans `app/public/service.py`, pas un `exclude`) ; les `questions[].id` uuid sont générés en service et **stables à vie** : les soumissions élèves (J5) et la review IA référenceront `(block_id, question_id)`, ne jamais les régénérer à l'édition), `document` (`{"legende", "affichage": inline|telechargement}` — pont vers une ressource de la bibliothèque, référencée par la **colonne** `resource_id`, jamais dans le content) et `module` (`{}` — réservé à de futurs réglages d'affichage : le module pointé vit dans la **colonne** `module_id`, jamais dans le content). CHECKs de cohérence symétriques `ck_blocks_document_coherence` / `ck_blocks_module_coherence` : **seuls les blocs `document` peuvent porter `resource_id`** et **seuls les blocs `module` peuvent porter `module_id`** — tous deux **nullables** (un bloc naît vide et se remplit dans l'éditeur) avec FK **`ON DELETE CASCADE`** (supprimer la ressource/le module supprime les blocs pointeurs — décision actée : un bloc pointeur sans sa cible n'a pas de sens). `resources` = **bibliothèque de fichiers S3 du cours, indépendante des blocs** : `s3_key` unique **préfixée par cours** (`courses/<course_id>/resources/<resource_id>/<nom-sanitizé>`), type ∈ document/image/audio/video (`module` retiré — les modules interactifs ne sont **pas** des ressources : leur bibliothèque vit dans la table `modules`, cf. ci-dessous), **`statut` `en_attente` → `disponible`** (la ligne est créée avant l'upload direct navigateur→S3, puis la confirmation HEAD S3 la passe à `disponible` — voir `app/resources/` ci-dessous). `modules` = **bibliothèque de modules interactifs du cours** (J4, anticipé), indépendante des blocs : `titre` String(255) + code **`html`/`css`/`js` en colonnes Text** (décision actée : en base, PAS de bundle S3 — le cadrage initial §5.5 a été réécrit), exécuté côté front en iframe sandbox à origine opaque. **Aucune relation ORM** sur ces modèles (lazy-load async interdit). Piège : autogenerate ne détecte pas la modification d'un `CheckConstraint` (il voit en revanche un changement de `ondelete` de FK) et ne génère jamais de migration de données — élargir `ck_blocks_type`/`ck_resources_type` = migration manuelle (la FK `blocks.resource_id`, créée sans nom, s'appelle `blocks_resource_id_fkey` en base). `share_links` (J2) est en place (`app/models/share_link.py`) : token opaque 256 bits stocké **en clair** (décision actée — capability URL recopiable à tout moment), `expires_at` **obligatoire** (`SHARE_LINK_TTL_DAYS`, 270 j), révocation soft `revoked` — la validité est vérifiée à chaque accès dans `app/public/service.py`, et `courses.visibilite` (`public`/`prive`/`en_cours`, CHECK `ck_courses_visibilite` posé **à la main** dans la migration — piège autogenerate ci-dessus) suspend les liens quand le cours repasse `en_cours`. Les colonnes **`search_vector`** (J3) de `courses` et `blocks` sont maintenues par **triggers PostgreSQL** (`BEFORE INSERT OR UPDATE OF …` — fonctions SQL `courses_tsvector`/`blocks_tsvector` de la migration, partagées avec le backfill), **jamais écrites par l'ORM** (`deferred=True` côté modèle : aucun service ne les lit) ; celui des blocs est construit **champ par champ** et n'indexe **jamais** `reponse_attendue` (cf. section Recherche publique).

### API des cours (`app/courses/`)
Toutes les routes résolvent d'abord `user = get_or_create_by_sub(db, auth)` puis scopent au propriétaire : un cours d'autrui est **introuvable (404, un seul select `id + owner_id`), jamais interdit (403)** — on ne divulgue pas son existence.
- `GET /api/v1/courses` (mes cours, tri `updated_at desc`, avec `subject_ids`/`education_level_ids`/`block_count`/`preview_settings`) ; `POST /courses` (201 — `subject_ids`/`education_level_ids` **optionnels**, dédoublonnés et validés par lookup, 422 « Matières inconnues »/« Niveaux d'étude inconnus » ; timestamps relus en RETURNING) ; `GET /courses/{id}` (détail **avec blocs** triés `position, id`).
- **Réglages de preview** (`PreviewSettings`) : `PUT /courses/{id}/preview` (200 — **remplacement complet** ; schéma strict `extra="forbid"`, clés **camelCase** = interface `CourseStyleSettings` du front via `alias_generator=to_camel`, les 6 champs **requis et bornés** (`fontSizePx` 8–48, `headingScale` 0.5–3, `lineHeight` 1–3, `widthCh` 20–200, `paragraphGapEm` 0–10, `font ∈ {sans,serif}`), 422 sinon ; réponse = les réglages enregistrés (`model_dump(by_alias=True)`, camelCase), **pas** le cours ; `_get_owned_course` puis mutation d'attribut ORM du JSONB — **nouveau dict** — et bump `course.updated_at`). Persistés dans la colonne **`courses.preview_settings`** (voir modèle) et **exposés en lecture** dans `CourseRead` — donc list **et** détail — en `dict[str, Any]` (écho brut, `{}` si non personnalisé ; `_course_read` et le `CourseRead` de `create_course` le portent). Ajouter un réglage = 1 champ dans `PreviewSettings`, **sans migration** (JSONB).
- Blocs : `POST /courses/{id}/blocks` (201 — type ∈ `texte|exercice|document|module`, tous créables ici : un bloc `document` naît **vide** (`resource_id` NULL) et se remplit dans l'éditeur ; `titre`/`description` optionnels posés dès la création ; contenu par défaut par type conforme à `block.py`, position = max+1) ; `PUT /courses/{id}/blocks/order` (204 — la liste doit contenir **exactement** les blocs du cours, positions réécrites 0..n-1 en un executemany Core sur la Table ; à garder déclarée avant un futur `PUT /blocks/{block_id}`) ; `PATCH /courses/{id}/blocks/{block_id}` (`BlockUpdate` — édition **partielle** : `titre`/`description` sur **tous les types**, `content` = **union de formes disjointes** `TexteContent | ExerciceContent | DocumentContent` (smart union sans discriminant, `extra="forbid"` des deux côtés — `DocumentContent` en **dernier** dans l'union, tous ses champs ont un défaut donc `{}` valide en document) dont la forme doit correspondre au type du bloc (422 sinon, levée **avant toute écriture** ; le content d'un bloc `module` reste non éditable — son contenu, c'est le module pointé) — pour l'exercice, le service préserve les ids de questions fournis (qui doivent exister dans le bloc, 422 « Questions inconnues » sinon), génère un uuid4 `str` pour les nouvelles (un `uuid.UUID` n'est pas JSON-sérialisable par asyncpg) et applique une sémantique **remplacement** (question absente = supprimée) ; **`resource_id`** (blocs `document` uniquement, 422 sinon) pointe/détache la ressource : `null` explicite détache, un uuid est validé en service — ressource du **même cours** et `disponible`, 422 « Ressource inconnue »/« Ressource non disponible » (422 et non 404 : le bloc, lui, existe — motif « Matières inconnues ») ; **`module_id`** est son miroir pour les blocs `module` (422 « module_id ne s'applique qu'aux blocs « module » » sinon ; module du même cours, 422 « Module inconnu », pas de statut à vérifier — le code vit en base) ; seuls les champs présents dans le payload sont appliqués via `model_fields_set`, un `titre`/`description`/`resource_id` explicitement `null` l'efface ; au moins un champ requis (422 sinon) ; `extra="forbid"`, `content` remplacé par un **nouveau dict** car la mutation in-place du JSONB n'est pas détectée par l'ORM) ; `DELETE /courses/{id}/blocks/{block_id}` (204 — pas de renumérotation, trous tolérés ; **ne touche jamais ni `resources` ni S3** : la ressource pointée par un bloc document reste dans la bibliothèque).
- **Toute mutation de blocs bump `course.updated_at`** (écriture d'attribut sur l'instance chargée par le contrôle de propriété) pour que le cours remonte dans la liste.
- **Nettoyage S3 aux suppressions** : `delete_course` énumère les `s3_key` du cours (et `delete_resource`, côté `app/resources/`, relit la sienne), puis `storage.delete_many` les purge du bucket **après le commit** (le cascade DB ne touche pas S3) — arbitrage : un échec S3 après commit laisse un orphelin dans le bucket, jamais une réf DB pointant un objet absent ; le vrai filet (job de réconciliation des orphelins) reste à écrire.
- Tests `tests/test_courses_api.py` : fausse session FIFO **étendue** — les `Update` sont tracés sans consommer la file, un `Insert` porteur de RETURNING (celui de `courses`) la consomme pour servir les timestamps ; `get_or_create_by_sub` consomme toujours le premier `[user]` de la file et commite une fois. Le faux client S3 est injecté via `app.dependency_overrides[get_storage]` (helper `_FakeStorage`, enregistre les clés supprimées).

### Stockage S3 (`app/core/storage.py`) et bibliothèque de ressources (`app/resources/`)
Bucket **privé**, jamais exposé : l'API mint des URL présignées, l'upload est **direct navigateur→S3** (on ne fait pas transiter les binaires par le backend — contrainte Pi : RAM/BP). **Exception actée** : l'export/import de cours (`app/course_transfer/`, cf. section dédiée) lit/écrit les binaires via l'API — `read_object_into`/`put_object`, seules méthodes de bytes du module — avec des volumes bornés par `TRANSFER_MAX_ZIP_BYTES`. Toute la logique boto3 est **confinée dans `app/core/storage.py`** (même exigence de remplaçabilité que l'IdP : c'est le **seul** module autorisé à importer `boto3`), exposée en dépendance `get_storage` (overridable en test comme `get_db`). `presign_put`/`presign_get` sont du **calcul local** (signature, aucune I/O) → appel sync OK dans un handler async ; `head`/`delete_many` parlent au réseau → déportés dans un thread (`run_in_threadpool`) pour ne pas bloquer l'event loop. `presign_get(s3_key, nom_original, inline=False)` : `inline=True` demande une disposition `inline` (le navigateur affiche l'objet — variante `?disposition=inline` de `/download`), `False` force le téléchargement (`attachment`).

`app/resources/` est le **CRUD de la bibliothèque du cours, indépendante des blocs** (une ressource existe sans bloc ; les blocs `document` la pointent via `PATCH .../blocks/{id}` côté `app/courses/`), scopé au propriétaire (404 jamais 403). Routes : `GET /api/v1/courses/{id}/resources` (liste, tri `created_at desc, id`, **`en_attente` incluses** — le front les affiche atténuées et permet de purger un upload raté ; jamais de `s3_key` dans `ResourceRead`, détail interne) ; le flow d'upload (Descriptions.md §5.2) — 1) `POST .../resources` (201) déclare le fichier (`nom_original`/`mime`/`taille`/`type ∈ document|image|audio|video` — **`module` exclu**, J4 ; `taille` ≤ `S3_MAX_UPLOAD_BYTES`), crée la ligne **`en_attente`** (clé `courses/<course_id>/resources/<resource_id>/<nom-sanitizé>`) et renvoie l'**URL présignée PUT** ; 2) le navigateur PUT le binaire sur cette URL ; 3) `POST .../resources/{rid}/confirm` (**200, sans body**) fait un **HEAD S3** — objet absent ou `ContentLength` ≠ `taille` déclarée → **409**, ressource déjà confirmée → 409 — et passe le statut à **`disponible`** (retour `ResourceRead` ; **ne crée AUCUN bloc**) — ; `PATCH .../resources/{rid}` (renommage : seul `nom_original` change, la **clé S3 reste figée**, le `Content-Disposition` des prochains downloads suit) ; `DELETE .../resources/{rid}` (204 — delete puis **purge S3 après commit**, motif `delete_course` ; les blocs `document` pointeurs partent avec elle par la FK `CASCADE`, aucun execute supplémentaire) ; `GET .../resources/{rid}/download` (**URL présignée GET en JSON**, TTL court, `?disposition=inline|attachment`, défaut `attachment` — `inline` demande un affichage navigateur et sert la route front de redirection qui matérialise les liens des PDF exportés ; 409 tant que la ressource n'est pas `disponible`). Côté prof, aucune route S3 sans Bearer : les anciennes gateways `/content` (307 authentifié) et `/public` (capability URL sans auth) ont été supprimées — l'accès élève sans compte passe par le régime public J2 (`GET /api/v1/public/courses/{id}/resources/{rid}/download`, presign sans Bearer, autorisé par visibilité/token — `app/public/`). ⚠ Ce régime expose **toute** la bibliothèque `disponible` du cours partagé, blocs ou pas (assumé, avertissement dans l'UI de partage du front). Toute mutation (confirm/rename/delete) bump `course.updated_at`. Ordre des `execute` documenté par fonction (contrat FIFO de `tests/test_resources_api.py`). Les mutations d'une ressource chargée en ORM passent par **mutation d'attribut** (pas d'UPDATE Core explicite — flush au commit).

Dev local : **MinIO** dans `docker-compose.yml` (multi-arch ARM64, console `:9001`) + job one-shot `minio-createbucket`. **Caveat** : une URL présignée mintée par l'api-en-conteneur pointe `minio:9000`, **injoignable par le navigateur** ; pour tester l'upload de bout en bout, lancer **uvicorn en local** (`config/development.yaml` → `localhost:9000`) — c'est le workflow de dev déjà en place (uvicorn local + Postgres docker sur `5429`).

### Bibliothèque de modules interactifs (`app/modules/`)
CRUD **pur BDD** de la bibliothèque de modules HTML/CSS/JS d'un cours (J4, anticipé — motif `app/resources/` sans storage : les modules sont indépendants des blocs, scopés au propriétaire, 404 jamais 403). Le code vit **en base** (`modules.html/css/js`, plafond `MAX_CODE_LENGTH = 200_000` caractères par champ) ; l'exécution est côté front (iframe sandbox à origine opaque — l'API ne sert jamais le code autrement qu'en JSON authentifié). Routes : `GET /api/v1/courses/{id}/modules` (liste **sans le code** — `ModuleSummary`, payload léger, tri `created_at desc, id`) ; `POST` (201, `ModuleRead` complet — le code peut naître vide, rempli par l'éditeur) ; `GET .../{module_id}` (détail avec code) ; `PATCH .../{module_id}` (édition **partielle** via `model_fields_set` : renommage et/ou autosave du code par le même endpoint ; **`null` rejeté sur tous les champs** — vider un code = envoyer `""`, pas de sémantique « null efface » ici — au moins un champ requis) ; `DELETE` (204 — les blocs `module` pointeurs partent par FK `CASCADE`, **rien à purger côté S3**). Toute mutation bump `course.updated_at` ; au PATCH, `module.updated_at` est posé **côté Python** (le `onupdate` SQL ne tirerait qu'au flush, APRÈS la construction de la réponse — qui renverrait sinon le timestamp de la sauvegarde précédente) ; `ModuleRead` construit **avant** commit (piège `MissingGreenlet`) ; ordre des `execute` documenté par fonction (contrat FIFO de `tests/test_modules_api.py`).

### Export/import de cours (`app/course_transfer/`)
**Exception actée à la règle « pas de binaire par le backend »** (choix utilisateur, contrainte Pi connue) : l'archive `.zip` d'un cours est assemblée et parsée par l'API. `GET /api/v1/courses/{id}/export` → `StreamingResponse` zip (`manifest.json` versionné — `format_version` 1, schémas `extra="forbid"` — en DEFLATE + une entrée `resources/<uuid>` par ressource **`disponible`** en STORE), assemblé en **un** `run_in_threadpool` dans un `SpooledTemporaryFile` (jamais une archive entière en RAM), fermé en `BackgroundTask` ; non exportés : `owner`, `visibilite`, `share_links`, `statut`, `s3_key`, ressources `en_attente` ; matières/niveaux portés par leurs **`code`** (uuid5 déterministes → portable entre instances). `POST /api/v1/courses/import` (multipart `UploadFile`, dépendance `python-multipart`) → **201 `CourseRead`** : recrée TOUJOURS un **nouveau cours** — uuid régénérés partout, colonnes `resource_id`/`module_id` remappées **et** références `oc-resource:`/`oc-module:` réécrites dans les chaînes markdown (`archive.rewrite_refs` ; réf inconnue laissée verbatim), `questions[].id` conservés (stables à vie), `visibilite='en_cours'`, codes de taxonomie inconnus ignorés. Sécurité d'import : seuls `manifest.json` et les entrées déclarées sont lus (jamais `namelist()`), tailles vérifiées deux fois (`file_size` du zip **et** compteur au flux décompressé), plafonds — 413 au-delà de `TRANSFER_MAX_ZIP_BYTES` (500 Mo), `S3_MAX_UPLOAD_BYTES` par fichier, limites de comptage `MAX_BLOCKS/RESOURCES/MODULES` — et 422 pour toute archive/manifest invalide. **Ordre transactionnel : inserts (sans commit) → put S3 → commit** — un échec S3 → rollback + purge best-effort des clés poussées → 503 ; au pire des orphelins bucket, jamais une réf DB pointant un objet absent (miroir de `delete_course`, qui purge APRÈS commit). Router monté **avant** `courses_router` (le littéral `/courses/import` doit primer sur un futur `POST /courses/{course_id}`). Ordre des `execute` documenté par fonction (contrat FIFO de `tests/test_course_transfer_api.py`). Le plafond dur du corps HTTP relève du nginx d'infra (Starlette spoole le multipart sur disque avant le handler).

### Recherche publique (`app/search/`) — J3
FTS Postgres sur les **cours publics** et les **profs opt-in**, même régime que `app/public/` : `APIRouter(prefix="/public/search")`, **aucune dépendance JWT** (la `customUrlValidation` du front n'attache pas de Bearer sous `/v1/public/`). Routes : `GET /api/v1/public/search/courses` et `/teachers` — query params `q` (≤200), `subject_id`, `education_level_id`, `limit` (1–50, défaut 20), `offset` (≤10 000) ; réponse = **première enveloppe paginée de l'API** `{items, total, limit, offset}` (précédent à réutiliser pour les futures listes). Config FTS **`french_unaccent`** (extension contrib `unaccent` + copie de `french`, créées par la migration J3 — stemming + insensibilité aux accents), requêtes `websearch_to_tsquery` (syntaxe libre, injection-safe, `q` blanc neutralisé en tête de service — `websearch_to_tsquery('')` ne matcherait rien). **Deux vecteurs stockés combinés à la requête** (cours OU un de ses blocs via `EXISTS`, rank = `ts_rank(cours) + 0.5 × max(ts_rank(blocs))`), **jamais consolidés** (un trigger d'agrégation re-calculerait tout le cours à chaque autosave). Règles de visibilité : cours → `visibilite='public'` seul filtre ; prof → `cherchable` (opt-in du profil, `ProfileUpdate.cherchable` défaut `False` — un PUT sans le champ « décoche », sémantique remplacement) AND `nom_public IS NOT NULL` AND `EXISTS(cours public)`, vecteur calculé **à la volée** (`to_tsvector(concat_ws(nom_public, string_agg(matières 'enseigne')))` — table minuscule, pas de trigger). **Pas d'oracle** : facette inconnue ⇒ page vide immédiate (jamais 422 — une URL partagée avec un id périmé reste servable). Facettes : matière = sous-arbre via `Subject.code` (`code == X OR code LIKE X || '.%'` — 2 petits selects, pas de CTE récursive ; codes `[a-z0-9.-]`, rien à échapper) ; niveau = `id == X OR parent_id == X` (2 profondeurs max). Les **arbres publics** `GET /public/subjects/tree` et `/public/education-levels/tree` (délégation pure dans `app/public/router.py`) alimentent les sélecteurs du front. Recherche **sans `q` autorisée** (catalogue trié `updated_at desc`). Assemblage des cartes = motif `list_public_courses_by_professor` (réutilise `PublicCourseRead` et `_course_read` de `app/public/`) ; ordre des `execute` documenté par fonction (contrat FIFO de `tests/test_search_api.py`). **Stratégie de test FTS sans Postgres** (précédent) : les builders purs `_courses_page_stmt`/`_teachers_page_stmt`… sont validés sur leur **SQL compilé** (`stmt.compile(dialect=postgresql.dialect())` — le nom de la config voyage en bind param, l'asserter via `compiled.params`), plus un garde-fou textuel qui scanne les corps `$$…$$` des `blocks_tsvector` de toutes les migrations : `reponse_attendue` ne doit jamais y figurer.

### Client IA générique (`app/core/ai/`) — BYO token, hors jalon
Brique transverse pour le futur J5 (RAG, résumés, quiz, review de copies) : client multi-provider **stateless** sur **LangChain 1.x**, approche « Bring Your Own Token ». **Seuls les modules de `app/core/ai/` importent `langchain*` et `langfuse`** (même exigence de remplaçabilité que boto3/IdP) ; les consommateurs n'importent que les ré-exports de `app.core.ai` (`AIClient`/`get_ai_client` — dépendance `lru_cache` overridable, motif `get_storage` — et les types `AIRequestConfig`/`ChatMessage`/`AICompletion`/`AIStreamEvent`). La config (provider, `api_key` en **`SecretStr`**, model, base_url, temperature/max_tokens) **voyage à chaque appel** ; à défaut, **cascade** (décision actée, remplace le « aucune clé persistée » initial) : config explicite de la requête > **credential utilisateur persistant chiffré** (`app/ai_credentials/`, cf. section suivante) > fallback serveur optionnel `AI_*` (résolu dans `AIClient.resolve_config`, vide = 422). Aucune clé n'est loggée ; `app/core/ai/` reste stateless — la cascade vit dans `app.ai_credentials.service.config_effective`, appelée par les consommateurs (routes `app/ai/`), jamais dans `AIClient` (singleton `lru_cache`). Providers (`providers.py`, factories à **imports paresseux**, instanciation directe des classes `Chat*` — **pas `init_chat_model`** : son provider huggingface part en backend `pipeline` = modèle transformers chargé en local, mortel sur Pi) : `anthropic`, `openai`, `google` (Gemini), `mistral`, `ollama` (base_url optionnelle : local ou distant, plafond = `num_predict`), `openai_compatible` (ChatOpenAI + **base_url requise** — Groq/vLLM/LM Studio…, clé absente → placeholder) et `huggingface` (**toujours** `HuggingFaceEndpoint`, jamais `from_model_id`). Deux modes : `complete()` (`ainvoke`) et `stream()` (**méthode sync à validation eager** — config résolue et modèle construit AVANT de retourner l'async generator, pour qu'une config invalide donne un vrai 4xx et non une erreur en plein flux SSE). **Erreurs traduites au bord** (`errors.py`, duck-typing `.status_code`/`.code`/`.response.status_code`, jamais 500, jamais le message brut du SDK dans les `detail`) : validation locale → 422 ; clé refusée par le provider (401/403) → **400, jamais 401** (réservé au JWT Zitadel — un 401 ferait re-loguer le front) ; autre 4xx provider → 422 neutre ; 429 → 429 ; injoignable/timeout/5xx/filet → 503. **Langfuse opt-in** (`observability.py`) : actif ssi les 3 settings `LANGFUSE_*` sont posés, sinon no-op sans même importer le SDK ; credentials passés explicitement depuis les settings ; trace rattachée au **`sub`** (jamais l'e-mail) via metadata `langfuse_user_id` ; flush au shutdown (`shutdown_langfuse()` dans le lifespan). Routes de smoke-test `app/ai/` (protégées prof, **supprimables** — retirer le mount + le package) : `POST /api/v1/ai/chat` et `POST /api/v1/ai/chat/stream` — ce dernier définit le **contrat SSE de référence** (`event: token|done|error`, data JSON compact, `\n\n`, flux clos après `done`/`error` ; l'événement `error` porte le status « qu'aurait eu » la requête, le 200 étant déjà parti) ; POST + fetch/ReadableStream côté front (EventSource ne porte pas de Bearer) ; headers `Cache-Control: no-store` + `X-Accel-Buffering: no` (le `proxy_read_timeout` du nginx d'infra doit couvrir une génération ; keepalive SSE périodique = évolution non implémentée). Tests : `tests/test_ai_client.py` (fake officiel `GenericFakeChatModel` de langchain_core — `ainvoke`+`astream`, découpe sur les espaces, pas d'usage — via monkeypatch de `build_chat_model`) et `tests/test_ai_api.py` (`_FakeAIClient` duck-typé via `dependency_overrides[get_ai_client]`, motif `_FakeStorage`).

### Credential IA de l'utilisateur (`app/ai_credentials/` + `app/core/crypto.py`)
Chaque utilisateur peut persister **une seule** config IA (colonnes `users.ai_provider/ai_model/ai_base_url/ai_api_key_chiffree/ai_chiffrement_sel`, CHECKs `ck_users_ai_coherence`/`ck_users_ai_cle_sel` posés à la main — les règles PAR provider restent en 422 service, jamais en CHECK). La clé API est chiffrée par **`app/core/crypto.py`** — **seul module autorisé à importer `cryptography`** (même confinement que boto3/IdP/langchain), fonctions pures — schéma v1 : AES-256-GCM, clé dérivée HKDF-SHA256(clé maître `AI_CREDENTIALS_MASTER_KEY` du `.env`, **sel par utilisateur** régénéré à chaque écriture de clé), blob versionné `0x01 || nonce(12) || ciphertext+tag`. Portée assumée : un dump DB seul ou le seul `.env` sont inexploitables ; un serveur compromis peut déchiffrer (inhérent — l'API doit lire la clé pour appeler le provider). Routes (`/users/me/ai-credentials`, motif `app/users/router.py`) : `GET` (200 toujours, projection `{provider, model, base_url, api_key_definie}` — **la clé, chiffrée ou non, ne figure dans AUCUN schéma de réponse, pas même un masque**), `PUT` (**`api_key` omise = clé existante conservée** — changer de modèle sans re-saisie ; blanche = 422 ; requise-mais-absente = 422 pour les providers cloud, ollama/openai_compatible en sont dispensés ; base_url requise pour openai_compatible, interdite ailleurs ; clé maître absente = 503), `DELETE` (204, les 5 colonnes à NULL — seule façon d'effacer la clé). La cascade `config_effective(db, auth, explicite)` alimente les routes IA : une config explicite court-circuite toute lecture DB ; un credential **illisible** (clé maître changée) → **422 « ré-enregistrez »**, jamais un repli silencieux sur `AI_*`. Tests : `tests/test_crypto.py`, `tests/test_ai_credentials_api.py` (fausse session FIFO + monkeypatch de `settings.AI_CREDENTIALS_MASTER_KEY`), cas cascade dans `tests/test_ai_api.py`.

### Tests sans dépendances externes
`tests/conftest.py` fournit : clé RSA de session + `make_token(...)` (signe des JWT RS256 avec `kid` de test, iss/aud/exp valides par défaut et surchargables), `mock_jwks` (monkeypatch de `jwks_cache.get_signing_key` — aucun réseau), `client`. Pour tester une route protégée sans crypto : `app.dependency_overrides[get_current_user]` ; pour une route qui lit la base : `app.dependency_overrides[get_db]` avec une fausse session (motif de référence : `tests/test_subjects_api.py`). Aucun test ne requiert Postgres ni Zitadel.

## Décisions actées (ne pas "corriger")

- **Pas de pgvector** : la vectorisation n'est pas actée ; si elle se fait ce sera probablement ChromaDB (jalon J5). Ne pas proposer d'extension Postgres — **une seule exception, actée au J3** : l'extension contrib `unaccent` + la config `french_unaccent` (migration FTS) ; toute autre extension reste à arbitrer explicitement avec l'utilisateur.
- **Pas de reverse proxy dans ce repo** : nginx est fourni et branché par l'infra ; le compose expose l'API sur le port 8000, c'est voulu.
- **Dépendances IA de `requirements.txt` (sentence-transformers, chromadb, redis, psycopg2-binary) volontairement conservées** bien qu'encore inutilisées — ne pas les purger. Les `langchain*` sont désormais consommées par `app/core/ai/` (ligne 1.x épinglée, décision actée : LangChain le plus récent) ; `langfuse` par `app/core/ai/observability.py`.
- **`scripts/` est écrit et maintenu à la main par l'utilisateur** — ne pas le modifier sans demande explicite.
- Contrainte transverse (Descriptions.md §5.8) : cible Raspberry Pi ARM64 — déporter le lourd (transferts via URL S3 présignées, jobs asynchrones), images Docker multi-arch.
- L'utilisateur s'occupe toujours de faire les commande alembic pour créer les migrations et les appliquer
